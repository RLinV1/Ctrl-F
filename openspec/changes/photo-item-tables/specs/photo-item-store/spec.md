# Spec Delta

## Purpose

Keeps a lasting record in Postgres of every photo the camera takes, every item found in it, and where each item was last seen, so Ctrl-F can answer from history.

## ADDED Requirements

### Requirement: Unique IDs
Every table SHALL use a UUID primary key generated by the database (`gen_random_uuid()`) when the writer doesn't supply one.

#### Scenario: New item
- **WHEN** an item row is inserted without an id
- **THEN** it gets a fresh UUID that no other row in that table shares

### Requirement: Store each processed photo
When the desktop finishes a photo and `DATABASE_URL` is set, it SHALL insert one `photos` row with the photo's S3 key, the annotated image's S3 key, the time the photo was taken, its width and height, and the model version. It SHALL store the key, never a URL.

#### Scenario: Photo stored
- **WHEN** the desktop processes `incoming/<job>.jpg`
- **THEN** a `photos` row exists with `s3_key = 'incoming/<job>.jpg'` and `job_id = <job>`

#### Scenario: Reprocessed photo
- **WHEN** the same S3 key is processed a second time
- **THEN** no second photo, detection, or lost-count change is written

### Requirement: Link photos to items through detections
The desktop SHALL insert one `detections` row per box in the photo with its label, confidence, normalized box `{x, y, w, h}`, and zone. `item_id` SHALL reference the tracked item whose name or alias equals the label (case-insensitive), and be null when there is none.

#### Scenario: Two items in one photo
- **WHEN** a photo shows keys and a wallet, both tracked
- **THEN** it has two detections, one linked to each item

#### Scenario: Untracked class
- **WHEN** a photo shows a "person" box and "person" isn't a tracked item
- **THEN** the detection is stored with a null `item_id`

### Requirement: Assign zones
Each detection SHALL get the first zone (ordered by creation time, then name) whose polygon contains the bottom-centre of its box, or null when no zone contains it.

#### Scenario: Box on the desk
- **WHEN** a zone "desk" covers the lower half of the frame and a box's bottom edge is centred inside it
- **THEN** the detection's `zone_id` is the desk zone

### Requirement: Keep each item's last location
For each tracked item found in a photo, the desktop SHALL set the item's `last_seen_at`, `last_photo_id`, and `last_zone_id` from that photo (using its most confident box), but only when the photo was taken after the stored `last_seen_at` or none is stored.

#### Scenario: Newer photo
- **WHEN** the keys were last seen at 9:00 on the couch and a 10:00 photo shows them on the desk
- **THEN** the keys' last location becomes the desk at 10:00

#### Scenario: Older photo processed late
- **WHEN** the keys were last seen at 10:00 and a photo taken at 8:00 is processed afterwards
- **THEN** the keys' last location stays at 10:00

### Requirement: Count lost items
For each requested target that's a tracked item and isn't detected in the job's photo, the desktop SHALL increment that item's `lost_count` by one.

#### Scenario: Wallet not visible
- **WHEN** the user asked for the wallet and the photo shows only keys
- **THEN** the wallet's `lost_count` goes up by one and the job is stored with `found = false`

### Requirement: Record the job
When the photo's file name is a job UUID, the desktop SHALL create or update that `jobs` row with `status = 'done'`, the requested targets, `found` (true when any target was detected), and `finished_at`.

#### Scenario: Job answered
- **WHEN** job `<id>` asked for keys and the keys were detected
- **THEN** `jobs.<id>` has `status = 'done'` and `found = true`

### Requirement: Database optional
When `DATABASE_URL` is unset, or a database write fails, the desktop SHALL still write its S3 results and keep processing new photos.

#### Scenario: Database down
- **WHEN** Postgres is unreachable while a photo is processed
- **THEN** the S3 result files are written, an error is logged, and the next photo is processed
